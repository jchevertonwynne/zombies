# Modules are grouped into folders by area, in one crate

The game's modules sit in a handful of folders, one per area of play: `weapons`, `enemies`, `players`, `economy`, `maps`, `run`, `ui`, `storage` and `net`. Each folder's `.rs` file only declares its modules, and a module keeps its own name inside its folder (`crate::enemies::zombie`, `crate::weapons::weapon`). Code used all over the game stays at the root: `state`, `authority`, `tuning`, `modifier`, `layers`, `audio` and `debug`. A new module goes in the folder for its area. It goes at the root only if most of the game reads it.

We chose folders over splitting the game into several crates. When this was decided, 58 of the 62 top-level modules reached each other in one cycle, and crates can't depend on each other in a cycle. Measured on the Mac with `--features dev`, an edit rebuilt in 15–20 seconds, almost all of it this crate's own codegen. Splitting it would have meant untangling most of the game first, for a rebuild that would still go through a core crate and the binary. The folders make the area of each module visible. They also make an import that reaches back into another area stand out, so the cycles can shrink over time. Once an area no longer depends on the rest of the game (`net`, `storage` and `nav` are the likeliest), it can become a crate cheaply.
